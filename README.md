# ESP-IDF Cooling Driver

A lightweight PWM-based cooling control module for ESP-IDF.

The driver controls one PWM cooling actuator, such as a fan or pump, from the temperature of one or more monitored devices. Each actuator can be associated with a cooling system containing multiple cooled devices. The driver evaluates the cooling demand of every registered device and applies the highest requested duty cycle.

The module uses the ESP32 LEDC peripheral for PWM generation and provides hysteresis, minimum-duty enforcement, configurable PWM polarity, and automatic LEDC channel allocation.

---

## Features

- Shared LEDC PWM timer initialization.
- Automatic LEDC channel allocation and release.
- Support for multiple cooled devices per actuator.
- Per-device activation and full-duty temperature limits.
- Linear duty-cycle increase above each device threshold.
- Hysteresis to prevent rapid on/off switching near the threshold.
- Configurable minimum duty cycle while cooling is active.
- 100% cooling demand at the configured full-duty temperature.
- Active-high and active-low PWM outputs.
- Compile-time configurable LEDC timer and PWM frequency.
- Runtime validation of cooling systems, devices, and actuators.
- ESP-IDF `esp_err_t` error handling.

## Core Concepts

The driver uses three public data types:

```c
cooled_device_t
cooling_system_t
cooling_actuator_t
```

### Cooled Device

A `cooled_device_t` represents a temperature-monitored component that needs cooling, such as a motor, inverter, battery, or other heat-generating device.

```c
typedef struct {
    char name[16];
    int32_t temperature_mc;
    int32_t threshold_temp_mc;
    int32_t full_duty_temp_mc;
} cooled_device_t;
```

All temperatures are expressed in milli-degrees Celsius.

Example:

```c
cooled_device_t inverter = {
    .name = "Inverter",
    .temperature_mc = 30000,
    .threshold_temp_mc = 45000,
    .full_duty_temp_mc = 70000,
};
```

The application is responsible for updating `temperature_mc` before calling `cooling_actuator_update()`.

The device configuration must satisfy:

```text
full_duty_temp_mc > threshold_temp_mc
```

### Cooling System

A `cooling_system_t` groups the devices cooled by the same actuator.

```c
typedef struct {
    const cooled_device_t **devices;
    size_t num_devices;
    size_t max_devices;
} cooling_system_t;
```

The cooling system stores pointers to devices; it does not own or copy the device objects. Every registered `cooled_device_t` must therefore remain valid for as long as it is part of the system.

The same device cannot be added twice to the same cooling system.

### Cooling Actuator

A `cooling_actuator_t` represents one PWM-controlled cooling output.

```c
typedef struct {
    char name[16];
    int gpio;
    uint8_t pwm_channel;
    bool initialized;
    bool active;

    cooling_system_t *cooling_system;

    uint32_t hysteresis_mc;
    uint32_t slope_pct_per_degC;

    uint8_t duty_cycle;
    uint8_t min_duty_cycle;
    bool pwm_inverted;
} cooling_actuator_t;
```

The LEDC channel is allocated internally by the driver.

`duty_cycle` always represents the logical cooling command:

```text
0%   = cooling off
100% = maximum cooling
```

This remains true when `pwm_inverted` is enabled; PWM polarity inversion is handled by the LEDC peripheral.

## PWM Configuration

The driver uses a fixed 8-bit LEDC duty resolution.

The default PWM configuration is:

```text
Timer:      LEDC_TIMER_0
Frequency:  25 kHz
Resolution: 8 bit
```
### PWM Configuration

The driver uses the following defaults:

```text
Timer:      LEDC_TIMER_0
Frequency:  25 kHz
Resolution: 8 bit
```

The LEDC timer and PWM frequency can be overridden at compile time.

To override them, add the desired compile definitions to the cooling component
in its CMakeLists.txt, after idf_component_register():

```cmake
target_compile_definitions(${COMPONENT_LIB} PRIVATE
    COOLING_LEDC_TIMER=LEDC_TIMER_1
    COOLING_LEDC_FREQ_HZ=20000
)
```
For example, the complete component CMakeLists.txt could be:
```cmake
idf_component_register(
    SRCS
        "cooling.c"

    INCLUDE_DIRS
        "include"

    REQUIRES
        esp_driver_ledc

    PRIV_REQUIRES
        esp_driver_gpio
)

target_compile_definitions(${COMPONENT_LIB} PRIVATE
    COOLING_LEDC_TIMER=LEDC_TIMER_1
    COOLING_LEDC_FREQ_HZ=20000
)
```

If no compile-time override is provided, the defaults defined in cooling.h
are used.

The PWM duty resolution is fixed internally at 8 bits.

If the requested PWM frequency cannot be generated by the LEDC peripheral with
the fixed 8-bit resolution, cooling_pwm_global_init() returns the corresponding
ESP-IDF LEDC error.

If the selected frequency cannot be generated by the LEDC peripheral with the driver's fixed 8-bit resolution, `cooling_pwm_global_init()` returns the corresponding ESP-IDF LEDC error.

The driver automatically selects high-speed LEDC mode on targets that support it and low-speed mode otherwise.

> **LEDC resource ownership:** the cooling driver manages its own LEDC channel allocation but cannot detect channels configured independently by other application code. Avoid independently using LEDC channels that may conflict with channels allocated by this component.

## Initialization Flow

Initialize the shared PWM timer first:

```c
ESP_ERROR_CHECK(cooling_pwm_global_init());
```

Create a cooling system:

```c
cooling_system_t cooling_system;
ESP_ERROR_CHECK(cooling_system_init(&cooling_system, 2));
```

Create the monitored devices:

```c
cooled_device_t inverter = {
    .name = "Inverter",
    .temperature_mc = 30000,
    .threshold_temp_mc = 45000,
    .full_duty_temp_mc = 70000,
};

cooled_device_t motor = {
    .name = "Motor",
    .temperature_mc = 28000,
    .threshold_temp_mc = 50000,
    .full_duty_temp_mc = 75000,
};
```

Register them in the cooling system:

```c
ESP_ERROR_CHECK(cooling_system_add_device(&cooling_system, &inverter));
ESP_ERROR_CHECK(cooling_system_add_device(&cooling_system, &motor));
```

Initialize the actuator:

```c
cooling_actuator_t fan;

ESP_ERROR_CHECK(cooling_actuator_init(
    &fan,
    "Main fan",
    FAN_PWM_GPIO,
    3000,   // 3 °C hysteresis
    10,     // +10 percentage points of duty per °C
    25,     // minimum 25% duty while active
    false   // active-high PWM
));
```

Assign the cooling system:

```c
ESP_ERROR_CHECK(cooling_actuator_set_system(&fan, &cooling_system));
```

Then periodically update the device temperatures and actuator:

```c
inverter.temperature_mc = read_inverter_temperature();
motor.temperature_mc = read_motor_temperature();

ESP_ERROR_CHECK(cooling_actuator_update(&fan));
```

## Control Logic

During each `cooling_actuator_update()` call, the driver:

1. Validates the actuator and assigned cooling system.
2. Validates every registered cooled device.
3. Updates the actuator active state using hysteresis.
4. Computes the requested duty cycle of every device.
5. Selects the highest requested duty cycle.
6. Enforces the configured minimum duty while the actuator is active.
7. Updates the LEDC PWM output.

### Device Duty Calculation

For each device:

```text
temperature <= threshold:
    proportional duty = 0%

temperature >= full-duty temperature:
    duty = 100%

otherwise:
    duty = (temperature - threshold) × slope_pct_per_degC
```

Because temperatures are stored in milli-degrees Celsius, the implementation converts the temperature difference to degrees Celsius when calculating the duty request.

The result is saturated at 100%.

The actuator applies the highest duty request among all registered devices.

---

## Hysteresis

An inactive actuator becomes active when at least one device rises above its threshold:

```text
temperature > threshold_temp_mc
```

Once active, it remains active until every registered device falls below:

```text
threshold_temp_mc - hysteresis_mc
```

While active, the applied duty is never lower than `min_duty_cycle`.

Example:

```text
Threshold:    50 °C
Hysteresis:    3 °C
Minimum duty: 25%

Temperature rises above 50 °C  -> actuator activates
Temperature falls to 49 °C     -> actuator remains active
Temperature falls to 47 °C     -> actuator remains active
Temperature falls below 47 °C  -> actuator deactivates
```

---

## PWM Polarity

For active-high control:

```c
pwm_inverted = false;
```

For active-low control:

```c
pwm_inverted = true;
```

PWM inversion is performed by the ESP-IDF LEDC peripheral. The driver's logical duty-cycle values remain unchanged:

```text
0%   = off
100% = maximum cooling
```

## Cooling System Management

Initialize:

```c
cooling_system_t system;
ESP_ERROR_CHECK(cooling_system_init(&system, max_devices));
```

Add a device:

```c
ESP_ERROR_CHECK(cooling_system_add_device(&system, &device));
```

Destroy:

```c
cooling_system_destroy(&system);
```

`cooling_system_destroy()` frees only the internal pointer array. It does not free any registered `cooled_device_t`.

Any actuator still referencing the cooling system must be detached or destroyed before the system is destroyed.

---

## Actuator Management

Initialize:

```c
cooling_actuator_t fan;

ESP_ERROR_CHECK(cooling_actuator_init(
    &fan,
    "Fan",
    FAN_GPIO,
    3000,
    10,
    25,
    false
));
```

Assign a cooling system:

```c
ESP_ERROR_CHECK(cooling_actuator_set_system(&fan, &system));
```

Detach the cooling system:

```c
ESP_ERROR_CHECK(cooling_actuator_detach_system(&fan));
```

Detaching sets the actuator output to 0%, clears the system reference, and resets the active state and stored duty cycle.

Destroy the actuator:

```c
cooling_actuator_destroy(&fan);
```

Destroying an actuator attempts to set its output to 0%, releases its internally allocated PWM channel, and resets the actuator structure.

The cooling system and cooled devices are not destroyed by `cooling_actuator_destroy()`.

## Complete Example

```c
#define FAN_PWM_GPIO 21

static cooled_device_t inverter = {
    .name = "Inverter",
    .temperature_mc = 30000,
    .threshold_temp_mc = 45000,
    .full_duty_temp_mc = 70000,
};

static cooled_device_t motor = {
    .name = "Motor",
    .temperature_mc = 28000,
    .threshold_temp_mc = 50000,
    .full_duty_temp_mc = 75000,
};

void cooling_example_task(void *arg)
{
    ESP_ERROR_CHECK(cooling_pwm_global_init());

    cooling_system_t system;
    ESP_ERROR_CHECK(cooling_system_init(&system, 2));

    ESP_ERROR_CHECK(cooling_system_add_device(&system, &inverter));
    ESP_ERROR_CHECK(cooling_system_add_device(&system, &motor));

    cooling_actuator_t fan;

    ESP_ERROR_CHECK(cooling_actuator_init(
        &fan,
        "Main fan",
        FAN_PWM_GPIO,
        3000,
        10,
        25,
        false
    ));

    ESP_ERROR_CHECK(cooling_actuator_set_system(&fan, &system));

    while (1) {
        /*
         * Update temperatures here before calling cooling_actuator_update().
         *
         * inverter.temperature_mc = read_inverter_temperature();
         * motor.temperature_mc = read_motor_temperature();
         */

        ESP_ERROR_CHECK(cooling_actuator_update(&fan));

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}
```

## Error Handling

Initialization and update functions use standard ESP-IDF `esp_err_t` return values.

Common errors include:

```text
ESP_OK                  Operation successful
ESP_ERR_INVALID_ARG     Invalid pointer, parameter, device configuration, or GPIO
ESP_ERR_INVALID_STATE   Object not initialized, invalid object state, or missing system
ESP_ERR_NO_MEM          Allocation failure, full cooling system, or no free PWM channel
```

LEDC functions may return additional ESP-IDF error codes.

Using `ESP_ERROR_CHECK()` is convenient during development, but production applications may choose to handle errors explicitly.

## Lifetime and Ownership

The cooling system owns only its internally allocated pointer array.

It does **not** own:

- `cooled_device_t` objects
- `cooling_actuator_t` objects

The application must ensure that:

- Registered devices remain valid while referenced by a cooling system.
- A cooling system remains valid while assigned to an actuator.
- An actuator is detached or destroyed before its cooling system is destroyed.
- Device temperatures are updated by the application before actuator updates.

Do not call an initialization function again on an already initialized object without first destroying the existing object.

---

## Thread Safety

The driver does not provide synchronization for its public object state or its internal PWM-channel allocator.

Do not concurrently initialize, destroy, reconfigure, or update the same cooling objects from multiple tasks without external synchronization.

---

## Notes

- The driver uses a fixed 8-bit PWM duty resolution.
- PWM timer and frequency are compile-time configurable.
- LEDC speed mode is selected automatically from the target SoC capabilities.
- PWM channels are allocated internally.
- `slope_pct_per_degC` represents **percentage-point duty increase per degree Celsius**, not per milli-degree Celsius.
- `full_duty_temp_mc` is the temperature at which the device requests 100% cooling duty; it is not an independent thermal shutdown or safety mechanism.
- Temperature acquisition and sensor fault handling are the responsibility of the application.
